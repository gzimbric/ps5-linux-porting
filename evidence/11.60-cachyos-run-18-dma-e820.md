# Firmware 11.60 DMA E820 loader build

Date: 2026-10-19

Run 18 booted CachyOS with an opt-in loader build that carries upstream's
13.60 low-memory DMA reservation, on the console used for Runs 15 to 17.
Linux received the intended e820 map, reached authenticated SSH over wired
Ethernet, and passed a short write and read-back check on the USB root
filesystem.

Run 18 is counted as the hardware validation of the DMA E820 build. It shows
that the build boots, that Linux sees the intended map, and that a short USB
write/read check passed. Run 15 remains the release baseline.

The build was made because testers reported read/write errors on the 11.60
port, and other developers said the same reservation fixed this on 13.60. No
exact error text has been received, and the errors have not been reproduced on
this console. Run 18 does not show that the build fixes them.

## The build

The ELF is built from loader branch `firmware-11.60-dma-e820` (commits
`1dad515` and `ab5aff6`, on top of `firmware-11.60-sonic-display` `489e7a7`)
with `make linux-1160-dma-e820`. It adopts the low-memory reservation from
upstream `ps5-linux-loader` commit `8cda4c1`. The built ELF is published as an
asset of the
[`firmware-11.60-dma-e820-run18` loader release](https://github.com/gzimbric/ps5-linux-loader/releases/tag/firmware-11.60-dma-e820-run18).

It was built on macOS with Homebrew LLVM 23.1.0, `x86_64-elf-gcc` 16.2.0, and
binutils 2.47. Other toolchain versions are not expected to reproduce the hash.
A build from a fresh clone at `ab5aff6` with that toolchain reproduced the
tested hash.

The change is to the memory map Linux receives below 1 GiB:

| Range | Run 15 build | DMA E820 build |
|---|---|---|
| `[0x00100000, 0x01000000)` | RAM | RAM |
| `[0x01000000, 0x3fffc000)` | RAM | Reserved |
| `[0x3fffc000, 0x40000000)` | Reserved | Reserved |

Linux therefore has about 1008 MiB less usable RAM.

Compared with the Run 15 ELF, the only differing bytes are the three E820
operands in the inner HV code, the wake blob that carries it, and the outer
build ID. The size and the gates are the same as Run 15: exact retail firmware
`0x11600005`, PS5 Pro (SoC `0x840fd0`) refused, a bzImage of exactly
12,702,720 bytes, and an initrd of exactly 54,376,639 bytes. The kernel and
initrd are checked by size, not by hash.

## Boot

The console was the same regular PS5 used for Runs 15 to 17: a CFI-1115B,
original model, digital edition, on retail 11.60.

After a cold boot and the kernel exploit, the DMA ELF was sent once to the
`ps5-payload-sdk` ELF loader on port 9021. Exactly 169,872 bytes were sent.
The console entered Rest Mode on its own and was then woken. One send was
recorded.

The loader printed 2,832 bytes, byte-identical to its output in Runs 16 and 17,
including `PS5 WiFi firmware offset missing for firmware 1160` and
`11.60 Sonic-style Linux wake chain armed`. The printed output does not show
the memory map; the e820 lines below come from Linux.

## Direct observations

Linux 7.1.7 started with the Arch/CachyOS userspace and this command line:

```text
root=LABEL=cachyos rw rootwait console=ttyTitania0 console=tty0 consoleblank=0 mitigations=off idle=halt preempt=full
```

The e820 map passed to Linux contained these lines (others omitted):

```text
BIOS-e820: [mem 0x0000000000100000-0x0000000000ffffff]  System RAM
BIOS-e820: [mem 0x0000000001000000-0x000000003fffffff]  device reserved
BIOS-e820: [mem 0x0000000040000000-0x000000005fffffff]  System RAM
```

This is exactly the intended reservation.

- An authenticated SSH session worked over wired Ethernet. `sshd`,
  NetworkManager, `ps5fan`, and `ps5-amdgpu-reprobe` were active.
- `MemTotal` was 14,783,608 kB, about 14.1 GiB. Run 16 reported about 15 GiB.
  `HardwareCorrupted` was 0 kB.
- The IOMMU default domain was passthrough.
- A scan of the kernel log over 22 minutes of uptime found no I/O errors,
  Buffer I/O errors, EXT4 errors or warnings, USB resets, xHCI errors, IOMMU
  faults, machine checks, or BUG/Oops lines. The ext4 state was clean.
- The journal errors in this boot were unrelated: desktop portal services
  that failed to start, a network-online wait timeout, and the known IW620
  IOCTL line.

### Wi-Fi

The unchanged Run 17 IW620 modules loaded; the kernel is byte-identical to
Run 17. The interface `wlp64s0f7` got a DHCP address. Autoload was configured,
but autoload across a reboot has not been observed. The known harmless
`IOCTL failed ... sub_id=0x200046 action=1, status_code=0x3` line appeared
again.

### Display

DRM reported `card0-DP-1` connected and enabled with DPMS on and a 1920x1080
mode, and a KDE Plasma desktop session started. Direct observation of the
picture was not recorded, so Run 18 is not counted as a visible-display
result. DRM state is not a substitute for direct observation.

## I/O check

The check ran on the USB root filesystem (ext4) under `/var/tmp`:

1. Write three 4 GiB files and record the SHA-256 of each.
2. Drop the page cache. The kernel logged `drop_caches: 3` between the write
   and read phases.
3. Re-read and re-hash all three files.

| File | Write | Re-read and hash | Result |
|---|---:|---:|---|
| 1 | 28 s | 15 s | Hash matched |
| 2 | 25 s | 15 s | Hash matched |
| 3 | 22 s | 16 s | Hash matched |

In total 12 GiB was written and read back in about 2 minutes. No new kernel
error or warning lines appeared during the test other than `kauditd`
rate-limit notices.

## Evidence limits

- This is one boot on the same console used for Runs 15 to 17, not a
  repeatability campaign or independent hardware reproduction.
- There is no A/B control. The Run 15 ELF was never put through the same I/O
  check, and the testers' read/write errors were never reproduced here. Run 18
  does not show that the reservation fixes them.
- The test was short: 12 GiB on the USB root only, in about 2 minutes. There
  was no soak, no M.2/NVMe storage, no GPU-heavy or gaming load, and no Wi-Fi
  under sustained traffic.
- The system was CachyOS, not Ubuntu. The CI-built Ubuntu image has not been
  booted with this ELF. The [tester guide](../docs/ubuntu2404-tester-guide.md)
  covers that combination.
- Physical display output was not recorded as observed.
- This is not an audit of the TMR ranges, and it does not show that missing
  reservations caused corruption.
- Raw logs are not published because they contain addresses and machine
  identifiers.
