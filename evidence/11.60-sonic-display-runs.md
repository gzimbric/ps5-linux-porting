# Firmware 11.60 Sonic display bring-up

Date: 2026-10-16

This is a sanitized hardware-evidence summary. It intentionally excludes raw
console logs, network addresses, local paths, and redistributable binaries.

## Current result

The official-loader/Sonic carrier now boots Linux on a regular retail PS5 with
firmware 11.60, and physical HDMI output now works. Runs 10, 12, 14, and 15
reached authenticated Linux userspace over wired Ethernet. Run 15 is the first
run to also produce visible physical display output.

Run 15 is the current hardware-verified baseline. Run 14 remains the
initializer-only control. Run 13 remains a repeated non-working diagnostic and
must not be described as a boot success.

## Direct observations

- Run 10 authenticated to Linux with boot ID
  `d62207c1-640c-48cc-8219-882f80365f33`.
- Run 12 authenticated to a different Linux boot with boot ID
  `9d427522-ede0-4ba8-813e-aa523b588dda`.
- Run 14 authenticated to Linux with boot ID
  `585b1bce-aa09-4310-8cbf-396b9523cc47` after TCP port 22 became reachable
  and remained up through the saved observation window.
- After Run 15 wake, the light turned steady white and the operator directly
  observed physical display output on the attached monitor. No photograph or
  machine timestamp of the first frame was captured.
- Run 15 authenticated to Linux with boot ID
  `546be1c9-68db-4b0b-b982-751c938616b8`. TCP port 22 came up about 52 seconds
  after the operator's wake cue and stayed up through the last recorded probe. The
  session reported `card0-DP-1` connected, enabled, and DPMS `On`, with
  Gamescope active on DP-1, the `amdgpudrmfb` framebuffer created, `/dev/sda1`
  mounted read/write, and `enp64s0f2` up. The bounded kernel audit found no
  captured panic or oops.
- The successful boots reported Linux 7.1.7 and the intended CachyOS root
  command line; Runs 10 and 12 also recorded 16 logical CPUs and about 15 GiB
  of RAM.
- In the successful display-audited boots, AMDGPU bound and the DRM
  connector reported connected. Run 12 also completed an explicit 1080p60,
  8-bpc, full-RGB modeset according to the driver. The physical monitor still
  reported no signal throughout that test, and Run 14 again reached a white
  light with `No Signal`. Run 15 is the first run where the same software
  state was accompanied by visible output.
- Run 11 never exposed TCP port 22. Its saved fast probe contains 65
  consecutive failures over roughly 148 seconds.
- The identical Run 13 ELF failed twice. The two saved probe windows contain
  79 and 87 consecutive TCP-port-22 failures, respectively, each spanning more
  than three minutes.
- The saved Run 13 wake differs from Run 12 at exactly one byte: zero-based
  file offset `0x1ee8` changes from `0x02` to `0x03`. The outer ELFs differ in
  that embedded byte and their GNU build IDs. Both Run 13 pre-rest captures
  are byte-identical.
- Run 14's clear-disabled wake and its same-source clear-enabled control differ
  at exactly one byte, raw offset `0x1f08` (`0x00` versus `0x01`). Three clean
  builds reproduced the Run 14 outer ELF, wake binary, and wake ELF
  byte-for-byte. Disassembly confirmed that the disabled-clear branch lands at
  the zero-argument initializer setup and exits PRE3 before command 21.
- Runs 10 through 14 used `OP=0`, so none intentionally called an entry in
  the 29-record display-operation table. Run 15 enabled all 29.

Authenticated userspace is conclusive evidence that the Linux handoff and
`startup_64` path completed in Runs 10, 12, 14, and 15. A white LED, a DRM
`connected` property, or a successful modeset return is not evidence of
visible output; Run 15's display result rests on direct operator observation.

## Controlled inference

Run 12 differs from Run 10 by enabling the 64-KiB VBIOS copy, transmitter call,
and Sonic-matching TSC wait. Because both reached authenticated Linux, those
PRE1/PRE2 operations are compatible with this boot path under the tested
conditions.

Run 13 added a PRE3 block that both cleared 10,252 bytes of MP3
request/response storage through the retained `linux_info` alias and called
`mp3_initialize(0)`. Run 14 kept PRE3 and the same direct initializer call but
disabled only the clear. Its authenticated Linux boot establishes that the
mapped 11.60 initializer can complete in this wake context.

Within this controlled sequence, the Run 13 regression is isolated to the
redundant clear and its 2,563 wake-time DWORD alias writes, not the initializer
itself. The complete 16-KiB page was already zeroed before suspend, and Sonic's
static request/response buffers begin zero-filled without a runtime clear.
The 11.60 production path must therefore match Sonic and omit that clear.
This is the supported causal conclusion from the controlled sequence; without
UART there is still no instruction-by-instruction trace, and ordinary resume
nondeterminism cannot be excluded absolutely.

Rather than continue the one-step ladder through command 21, command 22, and
the table, Run 15 enabled the complete remaining Sonic sequence at once:
commands 21 and 22, all 29 display-table records, Sonic's response-first buffer
layout, and its outer-call/leaf-tail-jump dispatcher, with the clear still
disabled. It produced visible display output and authenticated Linux in the
same cycle, so the full 11.60 path is hardware verified as a complete
containing sequence.

Because the remaining steps were enabled together, Run 15 does not attribute
the display result to any single command or table entry, and without UART it
does not expose individual return values. It is one successful cycle; it does
not yet establish repeatability, monitor coverage, or the minimal necessary
subset of the 29 operations.

The attached physical USB was subsequently resolved as a 248,145,510,400-byte
USB flash device, not the older mounted backup image with the same volume name
and UUID. Its 523,239,424-byte FAT32/EFI boot partition passed the complete
`diskutil verifyVolume` FAT check. A read-only snapshot of that physical
partition produced the exact file sizes and hashes above; no replacement was
needed. The active `cmdline.txt` and `vram.txt` also matched the Run 12 state,
with VRAM set to `0x20000000`. Runs 14 and 15 used these same inputs.

That audit directly verifies the physical FAT boot partition and active boot
inputs. The Linux root partition could not be mounted natively in the macOS
environment; its practical evidence remains the authenticated Run 12 boot,
root mount, userspace startup, and SSH session. The earlier `/Volumes/boot`
inspection is not used as physical-device evidence.

No physical UART was available. Pre-Linux UART cannot be obtained merely by
connecting a USB serial adapter to a PS5 host port because the console's USB
stack is not alive at this wake-stage boundary. Until a correctly identified
electrical UART is available, authenticated SSH is the Linux pass gate and
direct observation of physical output is the display pass gate; retained
memory breadcrumbs are the appropriate earlier-failure diagnostic.
