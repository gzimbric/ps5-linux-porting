# Firmware 11.60 Sonic display bring-up

Date: 2026-10-15

This is a sanitized hardware-evidence summary. It intentionally excludes raw
console logs, network addresses, local paths, and redistributable binaries.

## Current result

The official-loader/Sonic carrier now boots Linux on a regular retail PS5 with
firmware 11.60. Runs 10 and 12 reached authenticated Linux userspace over wired
Ethernet. HDMI output is not yet visible.

## Direct observations

- Run 10 authenticated to Linux with boot ID
  `d62207c1-640c-48cc-8219-882f80365f33`.
- Run 12 authenticated to a different Linux boot with boot ID
  `9d427522-ede0-4ba8-813e-aa523b588dda`.
- Both successful boots reported Linux 7.1.7, 16 logical CPUs, about 15 GiB of
  RAM, and the intended CachyOS root command line.
- In both successful boots, AMDGPU bound, an EDID was read, and the DRM
  connector reported connected. Run 12 also completed an explicit 1080p60,
  8-bpc, full-RGB modeset according to the driver. The physical monitor still
  reported no signal throughout that test.
- Run 11 never exposed TCP port 22. Its saved fast probe contains 65
  consecutive failures over roughly 148 seconds.
- The identical Run 13 ELF failed twice. The two saved probe windows contain
  79 and 87 consecutive TCP-port-22 failures, respectively, each spanning more
  than three minutes.
- The saved Run 13 wake differs from Run 12 at exactly one byte: zero-based
  file offset `0x1ee8` changes from `0x02` to `0x03`. The outer ELFs differ in
  that embedded byte and their GNU build IDs. Both Run 13 pre-rest captures
  are byte-identical.
- All four diagnostics used `OP=0`, so none intentionally called an entry in
  the 29-record display-operation table.

Authenticated userspace is conclusive evidence that the Linux handoff and
`startup_64` path completed in Runs 10 and 12. A white LED, a DRM `connected`
property, or a successful modeset return is not evidence of visible output.

## Controlled inference

Run 12 differs from Run 10 by enabling the 64-KiB VBIOS copy, transmitter call,
and Sonic-matching TSC wait. Because both reached authenticated Linux, those
PRE1/PRE2 operations are compatible with this boot path under the tested
conditions.

Run 13 adds the PRE3 block. In that build, PRE3 performs two actions: it clears
10,252 bytes of MP3 request/response storage through the retained
`linux_info` alias and then calls `mp3_initialize(0)`. The complete 16-KiB
`linux_info` page was already zeroed before suspend, and Sonic's static buffers
are pre-zeroed without an equivalent runtime clear. The two repeated Run 13
failures therefore narrow the regression to this combined PRE3 delta, but they
do not prove whether the alias writes, the MP3 initializer, or an earlier
unobserved event was the last executed operation.

The next bounded candidate is PRE3 with the runtime clear disabled and only
`mp3_initialize(0)` added to the proven PRE2 baseline. It is a planned or
unvalidated experiment until authenticated SSH says otherwise. If it passes,
commands 21 and 22 can be added separately. The 29-call table remains outside
the hardware-validated boundary.

The attached physical USB was subsequently resolved as a 248,145,510,400-byte
USB flash device, not the older mounted backup image with the same volume name
and UUID. Its 523,239,424-byte FAT32/EFI boot partition passed the complete
`diskutil verifyVolume` FAT check. A read-only snapshot of that physical
partition produced the exact file sizes and hashes above; no replacement was
needed. The active `cmdline.txt` and `vram.txt` also matched the Run 12 state,
with VRAM set to `0x20000000`.

That audit directly verifies the physical FAT boot partition and active boot
inputs. The Linux root partition could not be mounted natively in the macOS
environment; its practical evidence remains the authenticated Run 12 boot,
root mount, userspace startup, and SSH session. The earlier `/Volumes/boot`
inspection is not used as physical-device evidence.

No physical UART was available. Pre-Linux UART cannot be obtained merely by
connecting a USB serial adapter to a PS5 host port because the console's USB
stack is not alive at this wake-stage boundary. Until a correctly identified
electrical UART is available, authenticated SSH is the pass gate; retained
memory breadcrumbs are the appropriate earlier-failure diagnostic.
