# Firmware 11.60 CachyOS on Linux 7.3.0 with the bounded Wi-Fi loader

Date: 2026-10-19

Run 21 booted CachyOS on Linux 7.3.0 for the first time, on the console used
for Runs 15 to 19. It used a new loader build that checks the boot files
instead of requiring exact sizes, keeps the DMA E820 map from Run 18, and
copies the console's own Wi-Fi firmware to the USB drive. The operator
directly observed the HDMI picture, SSH worked over wired Ethernet, Linux
received the same e820 map as in Runs 18 and 19, and the onboard Wi-Fi came
up with the firmware the loader copied.

The kernel is mainline v7.3 with the 7.3 port of the PS5 patches by rmux
(Armandas Kvietkus), from
[rmuxnet/ps5-linux-patches-1](https://github.com/rmuxnet/ps5-linux-patches-1)
at commit `36f173f`. The same patch set brings rmux's PS5 CPU and GPU
frequency drivers, which were tried here at idle.

Run 21 is the first boot of the 7.3 line, which is meant for gaming. Run 15
remains the release baseline, Run 18 the DMA validation run, and Run 19 the
Ubuntu tester-pair run. Bluetooth does not work yet. The later large-install
watcher and game-load logger produced useful but limited observations; they
are not a storage-integrity pass, confirmed gameplay test, or stability test.

Run 21 also covers the Wi-Fi test that was planned as Run 22. Run 20, the
bounded loader with the Ubuntu image, was deferred.

### Loader

The ELF is `ps5-linux-loader-1160-dma-e820-bounded-wifi.elf`, built with
`make linux-1160-dma-e820-bounded-wifi` from
[gzimbric/ps5-linux-loader](https://github.com/gzimbric/ps5-linux-loader/tree/firmware-11.60-dma-e820)
branch `firmware-11.60-dma-e820` at commit `98925a2`. Compared with the Run 18
DMA E820 build, it:

- keeps the same DMA E820 map;
- shows every boot-file refusal as a notification, so payload menus show the
  reason;
- replaces the two exact-size gates with checks on the `bzImage` setup
  header, the `initrd.img` format, `vram.txt`, and `cmdline.txt`;
- sets the 11.60 IW620 firmware range, so the loader copies the console's own
  Wi-Fi firmware to `lib/nxp/` on the boot partition.

The source went through two rounds of adversarial review, and a CI build
reproduces the hash above. The public tester prerelease
[`firmware-11.60-dma-e820-bounded-run21`](https://github.com/gzimbric/ps5-linux-loader/releases/tag/firmware-11.60-dma-e820-bounded-run21)
holds this ELF and the build without
the Wi-Fi dump (`ps5-linux-loader-1160-dma-e820-bounded.elf`, SHA-256
`1c80b040c5a808b3f09418728424a875d5598fe6b2a5d68adeb4db5979a7541a`). That
second build was not booted.

The exact-size loaders, the Run 15 ELF (`422b87ec...`) and the DMA E820 ELF
(`2e1758a2...`), refuse these boot files.

### Image

The image was a local build of
[gzimbric/ps5-linux-image](https://github.com/gzimbric/ps5-linux-image/tree/cachyos-1160-k73)
branch `cachyos-1160-k73` from around commit `b97b6b0`, before that branch's
review fixes. It starts from the same official `ps5-cachyos` image as Run 18,
with the same partition and filesystem IDs. CI build 1 of the same branch,
with the review fixes (tag `cachyos1160-k73-image-1`), completed successfully
after this boot and is held in a draft release. It is not what booted, and it
has not been booted.

The later image 2 public tester prerelease is tagged
`cachyos1160-k73-image-2` at
commit `346088a48f66eb956dafdec9de5085e73b2d44a5`. It is also not what booted in
Run 21 and has not been booted since. Its source keeps rmux's published Linux
7.3 patch set at `36f173f`, then applies a separate hash-pinned IW620 Bluetooth
quirk follow-up; fixes the firmware-before-driver Wi-Fi load order; packages
the kernel as `linux-ps5 7.3.0-2`; and leaves the frequency drivers manual.
It also enables `ps5fan.service` with fixed maximum servo pattern `3`, not a
dynamic temperature curve.
The later CI result, prerelease publication and release-asset identities are
not Run 21 hardware evidence. They were verified separately after this run:
workflow `39481460775` completed successfully, and the
[public tester prerelease](https://github.com/gzimbric/ps5-linux-image/releases/tag/cachyos1160-k73-image-2)
has one
1,943,471,712-byte image archive with SHA-256
`8b785243f79a32a4155cc1e39bed01d580e25ca514e88abbfed1a8a8157a281a`.
Image 2 remains unbooted. The release policy is one `.img.xz`, never numbered
parts, and a prerelease until hardware results justify a status change. The
[image 2 tester guide](../docs/cachyos1160-k73-image-2-tester-guide.md) keeps
those new tests separate from this historical run.

The `bzImage` is a GCC 14.2 build of Linux v7.3 with `linux.patch` from rmux's
patch set at `36f173f`. rmux's CPU and GPU frequency drivers are built as
modules, and the VCN firmware (`ps5_vcn.bin`) is built into the kernel. The
earlier loaders needed an `initrd.img` of exactly 54,376,639 bytes. The bounded
loader does not, so this one is not padded.

The image was written to the same USB drive as Runs 16 to 19 with the flash
script that checks the image hash, and its audit passed. This overwrote the
Run 19 Ubuntu build 3 install.

## Boot

The console was the same regular PS5 used for Runs 15 to 19: a CFI-1115B,
original model, digital edition, on retail 11.60.

After a cold boot and the kernel exploit, the bounded Wi-Fi ELF was sent once
to the `ps5-payload-sdk` ELF loader on port 9021. Exactly 170,904 bytes were
sent. The loader printed 3,035 bytes, including these lines (others omitted):

```text
11.60 bounded: bzImage protocol 0x20f, setup 20480, payload 11592704 at 0x100000, decompress 0x1000000-0x36c5000
Dumped PS5 WiFi firmware to /mnt/usb0/lib/nxp/pcieuartiw620_combo_v1.bin (498108 bytes)
11.60 bounded: wake copy 0x100000000-0x103c9d000 (3878 logical pages)
11.60 Sonic-style Linux wake chain armed
```

- The first line is what the bounded check read from the `bzImage` setup
  header. The 20,480-byte setup and the 11,592,704-byte payload add up to the
  whole 11,613,184-byte file.
- The second line is the first time the loader copied the Wi-Fi firmware on
  11.60. The earlier 11.60 builds print
  `PS5 WiFi firmware offset missing for firmware 1160` instead.
- The wake copy ends at `0x103c9d000`. That is inside
  `[0x100000000, 0x1040048c0)`, the range the Run 15 files already covered on
  hardware, because both new boot files are smaller.

After Rest Mode, the operator woke the console with the controller's PS
button. The light turned white, and TCP port 22 opened about 25 seconds after
the wake was reported.

## Direct observations

CachyOS (Arch userspace) started with Linux 7.3.0 and the Run 15 command line,
which has no `nokaslr`:

```text
root=LABEL=cachyos rw rootwait console=ttyTitania0 console=tty0 consoleblank=0 mitigations=off idle=halt preempt=full
```

The e820 map passed to Linux contained these lines (others omitted):

```text
BIOS-e820: [mem 0x0000000000100000-0x0000000000ffffff]  System RAM
BIOS-e820: [mem 0x0000000001000000-0x000000003fffffff]  device reserved
BIOS-e820: [mem 0x0000000040000000-0x000000005fffffff]  System RAM
```

These are the same lines as in Runs 18 and 19.

KASLR placed the kernel code at physical `0x26ec00000-0x26fe70adf`, about
9.7 GiB, far above the reservation. With the DMA map, KASLR is what moves the
kernel out of the reserved range. Without it the decompressor leaves the
kernel at 16 MiB, inside `[0x01000000, 0x40000000)`, which is why the bounded
loader refuses `nokaslr` and kernels built without KASLR.

### Display

The operator directly observed the HDMI picture. Steam Gaming Mode came up on
the monitor. Run 21 is counted as a visible-display result.

### System

- The checks ran over SSH on wired Ethernet.
- `MemTotal` was 14,788,356 kB. Runs 18 and 19, on Linux 7.1.7, reported
  14,783,608 kB. `HardwareCorrupted` was 0 kB.
- The ext4 `cachyos` root had grown to 230.6 GB.
- The kernel log had no I/O, ext4, IOMMU, BUG, or Oops lines.
- The kernel taint value was 4160: the 64 seen in earlier runs, plus 4096,
  the out-of-tree module flag, set by the IW620 modules.
- Suspend is not supported on this boot path, so a `systemd-inhibit` lock on
  sleep, idle, and shutdown was held during testing.

## Wi-Fi

The firmware the loader wrote to the FAT partition,
`lib/nxp/pcieuartiw620_combo_v1.bin`, is 498,108 bytes with SHA-256
`eafef24af118f96f84a652e17aeed555ec4ac719b9fac11ff98a2de7e2b4b369`. That is
the same 11.60 p47 firmware used in Run 17.

At 12 seconds of uptime the driver probed before the firmware was in place:
`request_firmware` returned -2 and the probe failed with -14. At about 18
seconds the image's `ps5-iw620-firmware` service put the firmware in place and
reloaded the driver. The driver then reported `WLAN FW is active`, version
`PCIEIW620-17.130.3.p47`.

Scans saw 13 to 16 networks. Joining from the KDE network menu failed twice.
NetworkManager said the access point was not in the scan list. Joining by name
with `sudo nmcli --ask device wifi connect <SSID>` worked. Without `sudo`,
polkit refuses NetworkManager changes from an SSH session.

| Link | Value |
|---|---|
| Band | 5 GHz (5320 MHz) |
| Security | WPA3 |
| Rate | 1170 Mbit/s |
| Signal | 74 (NetworkManager's 0 to 100 scale) |

An HTTPS download bound to the Wi-Fi interface fetched 50,000,000 bytes at
23,979,239 bytes per second, about 192 Mbit/s. Run 17 got about 158 Mbit/s
with a smaller download. Both are single downloads, not a throughput test.
Wired Ethernet kept the default route (metric 100, against 600 for Wi-Fi).

## Video (VCN)

amdgpu found `vcn_v2_0` and reported
`Found VCN firmware Version ENC: 1.24 DEC: 8`. The VCN decode and encode rings
were set up, and no VCN errors were logged. No video was decoded, so this only
shows that the block starts.

## Bluetooth

Bluetooth does not work. `btusb` binds the USB companion `1286:2059` twice:
as `hci0` on interface 0 and as `hci1` on interface 2. Both fail during setup:

```text
hci0: Opcode 0x2031 failed: -22
hci1: Opcode 0x0c03 failed: -110
```

`btmgmt` reports `Index list with 0 items`, and `bluetoothctl` reports
`No default controller`. Run 19 on Linux 7.1.7 also logged opcode messages
from `hci0` and `hci1`, but Bluetooth was not tested there, so it is not known
whether this is new with 7.3.

## Controllers

A DualSense on a USB cable worked. `hid-playstation` registered the gamepad,
its motion sensors, the touchpad, and the headset jack, and reported
`fw_version=0x010f0000`. A Logitech USB receiver also worked. A wireless
DualSense could not be tried because Bluetooth does not work.

## Desktop switch

Steam's Switch to Desktop hung on its "switching to desktop" screen. The
image's `steamos-session-select` was not run, so the next-session token stayed
`gamescope`. Setting the token to `plasma` by hand and ending the tty1 session
started KDE Plasma (`kwin_wayland` and `plasmashell`), and the picture stayed
normal.

## Temperatures

These readings are `k10temp` `temp1`, sampled every 30 seconds for 10 minutes
per step, with the desktop or Gaming Mode idle. The fan service requested
servo pattern `3` (maximum), as in every run. The frequency drivers are
rmux's, from the same patch set as the kernel. This image builds them as
modules and does not load them at boot, so they were loaded by hand with
`modprobe`, one after the other.

| Step | Clocks | `temp1` |
|---|---|---|
| Linux 7.3.0, no frequency drivers | Not recorded | 49.5 to 50.25 °C after settling; 51.75 °C right after boot |
| Add `ps5_gpufreq` | GPU at 400 MHz | 45.0 °C at 30 s, 37.0 °C at 4 min, 35.75 to 36.5 °C at 10 min |
| Add `ps5_cpufreq` | CPU averaged about 820 to 860 MHz | 35.5 to 36.5 °C |

- The first step overlapped Steam's first-boot activity, with a load average
  of 0.3 to 1.7. For comparison, Run 19 on Linux 7.1.7 read 49.5 °C at idle.
- `ps5_gpufreq` registers the devfreq device `ps5-gpufreq` with the
  `simple_ondemand` governor and steps of 400, 800, 1200, 1600, 2000, and
  2230 MHz. At idle it held the GPU at 400 MHz, and the operator confirmed the
  picture stayed normal. It logged one line,
  `_allocate_opp_table: Error finding interconnect paths: -95`, which did not
  stop the driver.
- `ps5_cpufreq` registers the driver `ps5-cpufreq` with the `schedutil`
  governor, steps of 800, 1280, 1600, 1829, 1969, 2327, 2560, and 3200 MHz,
  and boost off. The CPU averaged about 820 to 860 MHz at idle and went up to
  about 3.18 GHz on demand.

At idle the GPU driver lowered the reading by about 14 °C. Adding the CPU
driver changed it by no more than about 0.5 °C.

## Later storage and load observations

Steam's content log recorded a completed update: 53,229,366,208 downloaded
bytes, 59,880,080,270 staged bytes, `Verifying Staged`, 347 committed files,
and a final `No Error` result. This is Steam's install pipeline, not an
operator-run **Verify integrity of game files** pass.

The storage watcher took 480 snapshots over about four hours. Free space on
the root filesystem moved from 213G to 159G, and every snapshot reported zero
new lines matching its storage-error patterns relative to the watcher's
baseline. Its throughput and total-byte
counters are invalid: the script read `/proc/diskstats` fields 7 and 11, which
are I/O time fields, instead of the sector counters in fields 6 and 10. The
run therefore does not establish a transfer rate, byte total, independent
read-back, or file hash.

The game-load logger took 540 samples at five-second intervals. `GameThread`
appeared in 88 samples. The GPU reported 2.23 GHz in 76 samples, and the final
frequency transition table recorded 386,159 ms at 2.23 GHz. Temperature rose
from a 35 °C minimum to an 84.0 °C peak; 30 samples were at or above 80 °C.
No GPU or IOMMU error was found in the checked log window. The logger ended
while the load was still active, and the operator did not confirm the picture
or gameplay during the load. This is load telemetry, not proof of gameplay,
thermal equilibrium, or sustained stability.

The frequency drivers remain manual-only. They have no thermal-cooling
integration, and Run 21 does not justify loading them automatically at boot.

Still untested: an operator-run Steam integrity check, an independent
read-back or hash check of the installed files, and an operator-observed game
session with a bounded thermal and stability run.

## Post-run image follow-up

Image 2 is tracked in the
[maintenance backlog](../docs/maintenance-backlog.md#run-21-cachyos-730).
The source includes the Bluetooth quirk follow-up, the Wi-Fi load-order fix,
the `linux-ps5 7.3.0-2` package identity, the decision to keep frequency
drivers manual, and the fixed maximum `ps5fan.service` bring-up setting. None
of those image 2 changes has been booted as part of the exact CI artifact.

Two image behaviors remain unresolved in the image 2 source:

1. Make Steam's Switch to Desktop run the image's session switch, so the
   next-session token changes to `plasma`.
2. Make joining Wi-Fi from the KDE network menu work. It fails, while a join
   by name works.

## Evidence limits

- This is one boot on the same console used for Runs 15 to 19, not a
  repeatability campaign or independent hardware reproduction. Other models
  have not been tested.
- The image was a local build from before the branch's review fixes, not a CI
  build. Neither CI image 1 nor image 2 has been booted.
- There is no A/B control, and the testers' read/write errors were not
  reproduced. The four-hour watcher saw no new matching storage-error lines
  after its baseline, but its throughput and total counters are invalid and
  it did no read-back or
  hash verification.
- Bluetooth does not work. Video decode was not exercised. The game logger
  captured a load and an 84.0 °C peak, but there was no operator-confirmed
  gameplay or display, no thermal equilibrium, and no stability run.
- Each temperature step ran once, in order, in one boot. The first step
  overlapped Steam's first-boot activity.
- Wi-Fi was one session on one network with one download. Joining from the
  desktop menu failed.
- There was no reboot or suspend test. Suspend is not supported on this path.
- The frequency drivers were loaded by hand. The image does not load them at
  boot, and Run 21 does not support enabling autoload yet.
- Raw logs are not published because they contain addresses and machine
  identifiers.
