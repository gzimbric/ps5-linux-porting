# Firmware 11.60 onboard Wi-Fi

Date: 2026-10-18

Run 17 booted the Run 16 Ubuntu USB with the exact Run 15 loader, then loaded
an out-of-tree IW620 driver over wired SSH. The driver downloaded the 11.60
firmware, registered a WLAN interface, scanned both bands, joined a 5 GHz
access point, and carried an HTTPS download bound to the Wi-Fi interface.

The same USB was used without being re-flashed. Run 17 did not re-hash the
boot files: the loader read a 12,702,720-byte bzImage and a 54,376,639-byte
initrd, the same sizes as in Run 16, its whole output was byte-identical to
Run 16, and the kernel reported 7.1.7. Before the autoload step, the only
additions were the driver modules and the firmware file on the root
filesystem. Build and setup steps are in the
[Wi-Fi guide](../docs/ubuntu2404-wifi.md).

The modules were built from `ps5-linux-mwifiex` `4aff908` and NXP
`lf-6.18.2_1.0.0` `a5fe4e1` with four of the five upstream patches; the 7.2
compatibility patch was left out. The firmware was carved from this console's
11.60 kernel-data dump. Neither the modules nor the firmware are
redistributed.

## Boot

The first attempt used a cold boot, the kernel exploit, the loader send, and
automatic Rest Mode, as before. The loader printed the same 2,832 bytes as in
Run 16, including `11.60 Sonic-style Linux wake chain armed`, and then entered
Rest Mode. After wake the console stayed on a continuously pulsing blue light
and never answered on the network. It was powered off by holding the power
button.

The second attempt repeated the cold boot and sent the same ELF. Its loader
output was again byte-identical to Run 16. TCP port 22 opened about 23 seconds
after the operator reported the wake.

For the first wake the operator had been told to press the console power
button. For the second, the instruction was the controller's PS button, as in
Runs 15 and 16, with the monitor on and set to the PS5 input. Neither was
confirmed afterwards, so the cause of the stall was not isolated. Runs 15 and
16 each woke on the first attempt.

## Direct observations

Loading `mlan` and `moal` with the documented options produced these lines,
in order (progress lines omitted):

```text
wlan: Loading MWLAN driver
FW download over, size 498108 bytes
WLAN FW is active
Register NXP 802.11 Adapter mlan0
wlan: version = PCIEIW620-17.130.3.p47--MM6X17542.p8-GPL-(FP92)
wlan: Driver loaded successfully
```

- About 7.5 seconds passed from the first line to the last.
- The driver downloaded the firmware and did not report it already running.
  That is consistent with the WLAN firmware not running when Linux started
  after the 11.60 wake path.
- udev renamed `mlan0` to `wlp64s0f7`. NetworkManager managed it and started
  a scan on its own.
- The `mrvl_pcie_msi` vector for `0000:40:00.7` had counted 88 interrupts by
  the time of the scan.
- The only driver error line was
  `IOCTL failed ... sub_id=0x200046 action=1, status_code=0x3`, logged just
  before the adapter registered. Upstream identifies it as the firmware
  rejecting the channel-region download and treats it as harmless. Scanning
  and association still succeeded.
- The kernel taint value was 64 before the load. Loading the modules added
  only 4096, the out-of-tree flag.

Scanning listed at least 24 BSS entries on 2.4 GHz channels 1 to 11 and 5 GHz
channels 40 to 165. The operator then joined a network from the GNOME Wi-Fi
menu:

- The driver logged `HostMlme ... Connected ... successfully` at 155 seconds
  of uptime, after the network was selected.
- The link was on 5 GHz channel 64 at a reported 270 Mbit/s. The access point
  advertised WPA3.
- The connection came up through NetworkManager with a DHCP address. The Wi-Fi
  default route had metric 600 and the wired route kept metric 100, so SSH
  stayed on Ethernet.
- A 20,000,000-byte HTTPS download with `curl --interface wlp64s0f7` returned
  HTTP 200 at 19,740,725 bytes per second (about 158 Mbit/s).
- No new driver error lines appeared after the connection.

The HTTPS download bound to `wlp64s0f7` is the pass gate. Association, the
DHCP address, and the interrupt count corroborate it but would not, by
themselves, show traffic over Wi-Fi.

Autoload was then configured: the modules were installed under
`/lib/modules/7.1.7/updates/ps5-iw620`, the options were written to
`/etc/modprobe.d/ps5-iw620.conf`, `moal` was added to `modules-load.d`, and
the blacklist file was replaced in place with a comment line.
`modprobe --show-depends moal` resolved to the installed modules with the
tested options, and no blacklist entry for `moal` or `mlan` remained. The
network profile created from the menu was set to connect automatically.

Run 17 used shorter versions of the scripts in `tools/`, with the same file
checks, install locations, and module options. The kernel-version, vermagic,
and depmod checks in the published scripts have not run on the console.

## Evidence limits

- This is one session on the same console used for Runs 15 and 16, not a
  repeatability campaign or independent hardware reproduction. There was no
  soak test, no reboot with autoload enabled, and no unload and reload of the
  driver.
- The concurrent-traffic firmware wedge reported upstream was not exercised.
- The loader's own firmware dump for 11.60 was not used. The Run 15 loader
  printed `PS5 WiFi firmware offset missing for firmware 1160` as in Run 16,
  and the firmware file was copied onto the root filesystem instead.
- `ping` is not installed in the image, so no ICMP test was run. The
  download is the traffic evidence.
- Bluetooth was not tested.
- Raw logs are not published because they contain addresses, network names,
  and machine identifiers.
