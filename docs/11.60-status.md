# Firmware 11.60 status

Last updated: 2026-10-20

Console class: regular PS5

Overall status: Linux boot and visible physical HDMI are hardware-verified on
retail firmware 11.60.

Current direction: preserve the exact full-fidelity Run 15 path: no redundant
runtime clear, Sonic's response-first MP3 buffer geometry, and its outer-call /
leaf-tail-jump display dispatcher. Run 15 is the current hardware-verified
baseline. Run 14 remains the initializer-only control, and the identical Run
13 artifact remains a repeatable non-working clear-enabled result. The
pLinux-derived wake wrapper remains superseded. Run 16 reused the byte-identical
Run 15 loader to boot Ubuntu 24.04 with authenticated SSH and visible physical
output, providing a cross-distribution control without changing the loader.
Run 17 kept that loader and the Run 16 Ubuntu USB and brought up the onboard
IW620 Wi-Fi with separately built driver modules. Run 18 booted CachyOS with a
loader build that carries upstream's 13.60 low-memory DMA reservation. It is
an opt-in build for testers; Run 15 remains the release baseline. Run 19
booted that build with the CI-built Ubuntu 24.04 image from the tester guide,
and the operator saw the picture on the monitor.

The main line is moving to CachyOS on Linux 7.3.0 for gaming. It is built on
the 7.3 port of the PS5 patches and the CPU and GPU frequency drivers by rmux
(Armandas Kvietkus), from
[rmuxnet/ps5-linux-patches-1](https://github.com/rmuxnet/ps5-linux-patches-1).
Run 21 was its first boot, with a bounded loader build that checks the boot
files instead of their sizes and copies the Wi-Fi firmware. Run 15 remains the
release baseline, Run 18 the DMA validation run, and Run 19 the Ubuntu
tester-pair run. Run 20, the bounded loader with the Ubuntu image, was
deferred. The image 2 public tester prerelease is tagged
`cachyos1160-k73-image-2` at
`346088a48f66eb956dafdec9de5085e73b2d44a5`. Its CI run completed
successfully and the release archive and raw-image identities are verified,
but no identity-verified hardware boot is recorded.

Image 3 is now the active source candidate, pinned on image-repo `main` at
`f7d6fbd9d630cddaceb83f3b861869d4453af8ca`. It is not built, tagged,
published, or tested on hardware. The source identifies its kernel package as
`linux-ps5 7.3.0-3`; rebuilds the exact Bazzite Deck v1.0.3 Bluetooth patch
asset (SHA-256
`c01bdcc134f25a86825f2824d12a82da02db18e7b1940db722223b0c4611eed8`)
rather than copying a prebuilt module; and keeps the NXP driver base at
`a5fe4e1` while pinning the IW620 patch stack at
`4bce848dd098bf74fbafd0078463da3d9f0d7f80`, including the HE and TX fixes.
The BlueZ side matches the working Bazzite policy with an always-pairable dual
controller, device privacy, accepted Just-Works repairs, auto-enable, and
`UserspaceHID=true`. It uses the pairing agent supplied by KDE or
`bluetoothctl` and `uhid`/`hid-playstation`, not a custom pairing daemon or an
`hidp` preload. NetworkManager uses
`wifi.powersave=2`. Its intended startup policy is a fixed
maximum fan request
followed by guarded GPU-then-CPU scaling, with
`/boot/efi/disable-ps5-performance` as a persistent opt-out. It also adds a
narrow Steam-to-Plasma handoff, masks Linux sleep targets, and keeps the
hosted release as one `.img.xz`. These are source facts only until one exact
hosted artifact receives hashes and passes the hardware gates in the
[image 3 tester guide](cachyos1160-k73-image-3-tester-guide.md).
Kernel-cache run `39505071885` is still in progress; the full image run has not
started, and there is no image-3 tag or release.

## Ubuntu control run

Run 16 used the byte-identical 169,872-byte Run 15 ELF with SHA-256
`422b87ec39ca0edfce8dddd609c2eff1cc7adcb2732b7909b76fafbd60dd2336`.
It reached Ubuntu 24.04.5 userspace over wired SSH and produced directly
observed physical output. The authenticated system reported Linux 7.1.7,
16 logical CPUs, about 15 GiB of RAM, a read/write expanded root filesystem,
and an active GDM/GNOME Wayland session on the connected 1920x1080 display.

The Ubuntu EFI initrd has the same loader-gated size as Run 15, 54,376,639
bytes, but SHA-256
`2eef0352879e091083450b799c75514a450f4110cbc747f640962fdde2dc06c8`.
It consists of a 50,803,483-byte Ubuntu initramfs followed by 3,573,156 zero
bytes. It is not the exact CachyOS initrd described in the Issue #1 recipe, so
Run 16 is additional loader and distribution evidence rather than a
reproduction of that issue's input.

This was a custom Ubuntu 24.04 image, not the stock output of the pinned
upstream image-builder revision. Its exact USB identities, source revision,
separate clean-build validation gates, and read-only comparison tool
are in the [Run 16 Ubuntu USB guide](ubuntu2404-run16-usb.md).

The live hardware inventory identified PCI wireless function `1b4b:2b56` and
USB companion `1286:2059`. These are Marvell identifiers, not MediaTek MT7921
identifiers, so the mt76/MT7921 driver cannot bind this console. The hardware
pairing is consistent with the
[PS5 IW620 mwifiex path](https://github.com/ps5-linux/ps5-linux-mwifiex).
See the [sanitized Run 16 evidence](../evidence/11.60-ubuntu-run-16.md) for the
tested input hashes and observation limits.

Relative to the Run 14 control, the finalized source keeps the clear disabled,
places the 0x1408-byte response buffer first at retained-page offset `0x1000`,
leaves an 0x18-byte gap, places the 0x1404-byte request buffer at `0x2420`, and
uses Sonic's outer `CALL` / leaf tail-`JMP` dispatcher. With commands 21 and 22
and all 29 records enabled, that exact path is now hardware verified as a
complete containing sequence.

See the [sanitized run matrix](../evidence/11.60-sonic-display-runs.md) for
artifact hashes, direct observations, controlled inferences, media identities,
and no-UART limits.

## Wi-Fi run

Run 17 sent the same Run 15 ELF and booted the same Ubuntu USB. After the
first wake the console stayed on a continuously pulsing blue light with no
network and had to be forced off. The second attempt, after a cold boot,
opened TCP port 22 about 23 seconds after the operator reported the wake. The
cause of the first stall was not isolated.

Over wired SSH in the second boot, `mlan` and `moal` built for the exact Run
16 kernel tree were loaded with the upstream PS5 options. The driver
downloaded the 498,108-byte firmware, reported `PCIEIW620-17.130.3.p47`, and
registered `mlan0`, which udev renamed to `wlp64s0f7`. It scanned both bands,
joined a 5 GHz network on channel 64, and carried a 20,000,000-byte HTTPS
download at about 158 Mbit/s. Autoload was then configured but has not yet
been observed across a reboot. The build, firmware location, and setup are in
the [Wi-Fi guide](ubuntu2404-wifi.md); observations and limits are in the
[Run 17 evidence](../evidence/11.60-ubuntu-run-17-wifi.md).

## DMA E820 build run

Testers reported read/write errors on the 11.60 port. Other developers said
this was fixed on 13.60 by upstream's low-memory reservation in
`ps5-linux-loader` commit `8cda4c1`. No exact error text has been received,
and the errors have not been reproduced on this console.

The opt-in DMA E820 build adopts that reservation. Linux gets RAM only at
`[0x00100000, 0x01000000)` in low memory and sees `[0x01000000, 0x40000000)`
as reserved. The Run 15 map has RAM up to `0x3fffc000`. The ELF is 169,872
bytes with SHA-256
`2e1758a2d013305bcb9faa0eb3adf18c34ed76ad85313dd945719c8bf2a0c9c0`. It
differs from the Run 15 ELF only in the three E820 operands in the inner HV
code, the wake blob that carries it, and the build ID, and it keeps the same
firmware, model, and boot-file size gates. It is published as an asset of the
[`firmware-11.60-dma-e820-run18` loader release](https://github.com/gzimbric/ps5-linux-loader/releases/tag/firmware-11.60-dma-e820-run18).

Run 18 sent that ELF once to the same console. The USB held CachyOS built
from the official `ps5-linux-image` CachyOS release image, with the exact Run
15 FAT boot files. The loader output was byte-identical to Runs 16 and 17.
Linux 7.1.7 reported the intended e820 lines and about 14.1 GiB of RAM, against
about 15 GiB in Run 16, and authenticated SSH worked over wired Ethernet.
Three 4 GiB files written to the USB root were re-read after dropping caches,
and all hashes matched. The kernel log showed no storage, USB, IOMMU, or
machine-check errors over 22 minutes. DRM reported an active 1920x1080 output
and a KDE Plasma session, but the picture was not recorded as directly
observed.

Run 18 is counted as the hardware validation of the DMA E820 build. It does
not show that the reservation fixes the reported errors: there was no A/B
control with the Run 15 ELF and the test was short. The
[tester guide](ubuntu2404-tester-guide.md) covers this ELF with the CI-built
Ubuntu 24.04 image; Run 19 booted that pair. Observations and limits are in
the [Run 18 evidence](../evidence/11.60-cachyos-run-18-dma-e820.md).

## CI Ubuntu image run

Run 19 booted the image and ELF from the tester guide: CI Ubuntu build 3 from
the
[`ubuntu2404-1160-build-3` release](https://github.com/gzimbric/ps5-linux-image/releases/tag/ubuntu2404-1160-build-3)
and the DMA E820 ELF from the Run 18 loader release. CI built the image from
`ps5-linux-image` commit `ec8cd4e`. Its `bzImage` is the same as in Runs 15 to
18 and its `cmdline.txt` the same as in Run 16. Its `initrd.img` is a new
build of the same 54,376,639-byte size. The image was flashed to the same USB
drive as Runs 16 to 18, and a byte compare and read-back hash matched.

The ELF was sent once to the same console. The loader output was
byte-identical to Run 18. The console entered Rest Mode by itself and was
woken once with the controller's PS button; the light turned white and TCP
port 22 opened about 20 seconds later. The operator directly observed the HDMI
picture. DRM reported `card0-DP-1` connected at 1920x1080, and a GNOME session
was logged in automatically on `seat0`. Ubuntu 24.04.5 with Linux 7.1.7
reported the same e820 lines and `MemTotal` as Run 18.

The checks in the tester guide were run as written. All passed. The optional
I/O check wrote three 4 GiB files, re-read them after dropping the page cache,
and matched all three. The whole check took 1 minute 45 seconds. A scan of the
kernel log for the whole boot found no storage, IOMMU, or machine-check errors
and no BUG, Oops, or Call Trace lines. `systemctl --failed` was empty.

Two defects in the image profile were found. The hostname is the ID of the CI
build container; the Run 16 image also had a container-ID hostname, so this is
a profile issue and not new to CI. The other is a systemd ordering cycle
involving `ssh.socket` and `ps5-ssh-host-keys.service`, which was not seen in
Run 16. SSH still worked. Both are in the
[maintenance backlog](maintenance-backlog.md#run-19-ci-ubuntu-image).

Run 19 is a visible-display pass and the first recorded hardware boot of a
CI-built Ubuntu image. Run 18 remains the DMA validation run and Run 15 the
release baseline. Run 19 is one boot on one CFI-1115B with no A/B control, and
other models have not been tested. Observations and limits are in the
[Run 19 evidence](../evidence/11.60-ubuntu-ci-run-19.md).

## CachyOS 7.3.0 run

Run 21 is the first boot of CachyOS on Linux 7.3.0. The kernel is a GCC 14.2
build of mainline v7.3 with the 7.3 port of the PS5 patches by rmux (Armandas
Kvietkus), `linux.patch` from
[rmuxnet/ps5-linux-patches-1](https://github.com/rmuxnet/ps5-linux-patches-1)
at commit `36f173f`. The same patch set has rmux's PS5 CPU and GPU frequency
drivers, which the Run 21 image built as modules and did not load at boot. The
VCN firmware is built into the kernel. Run 21 also covers the Wi-Fi test that
was planned as Run 22.

The image was a local build of `ps5-linux-image` branch `cachyos-1160-k73`
from before that branch's review fixes, on the same official `ps5-cachyos`
base as Run 18. CI build 1 of the branch, with the review fixes, completed
successfully afterwards and is held in a draft release; it has not been
booted. The image's 11,613,184-byte `bzImage` and
51,900,862-byte `initrd.img` are not the sizes the Run 15 and DMA E820 ELFs
accept, and both of those ELFs refuse them.

The public tester prerelease is image 2, tag `cachyos1160-k73-image-2` at commit
`346088a48f66eb956dafdec9de5085e73b2d44a5`. It still applies rmux's published
Linux 7.3 patch set at `36f173f` as the base. A separate local, hash-pinned
follow-up restores the IW620 quirks-table entry and post-lookup interface
checks present in merged [ps5-linux patch-set PR #35](https://github.com/ps5-linux/ps5-linux-patches/pull/35)
but absent from the pinned rmux 7.3 patch, while retaining rmux's 7.3 IW620
quirk flags. Image 2 also prevents alias-driven `moal`
loading until the loader-dumped firmware is copied, then loads it explicitly;
uses package identity `linux-ps5 7.3.0-2` with `KBUILD_BUILD_VERSION=2`; and
keeps `ps5_cpufreq` and `ps5_gpufreq` manual-only. These are source/build
changes, not hardware results. Image 2 also enables `ps5fan.service` by
default. That service requests tested maximum servo pattern `3`; it is a fixed
bring-up setting, not a temperature-driven fan curve. Workflow `39481460775`

## Historical irreversible takeover attempt

The last useful log reached these checkpoints:

```text
existing bypass verified
live HV VMMCALL handler validated
staging identity map and HV loader
bzImage copy complete
Linux images staged successfully
```

There was no later marker. The console stopped responding. This does not prove
that the handler redirect ran. It places the fault somewhere after staging and
before the next observable result. This was a split-flow build that performed
the bypass and Linux attempt as separate userland-visible stages.

## Superseded candidate: pLinux-derived wake wrapper

The candidate changed the ordering rather than treating the previous silence
as another offset problem:

1. Before rest mode, load the Linux inputs and retain page-granular physical
   source copies plus a compact resume parameter block.
2. Hook the 11.60 S3 `HV_MP_STARTUP_CALL` resume path with a position-independent
   kernel-text wrapper.
3. On wake, call the displaced startup function with its original arguments.
4. Complete and verify the exact 16-of-16 Byepervisor strike.
5. Restore the resume hook before attempting the irreversible handoff.
6. Build the identity PML4, clone the live hypervisor high mappings, and refresh
   the Linux payload, bzImage, and initrd from the retained copies.
7. Validate the live VMMCALL handler, install the transition redirect, and use
   the kernel all-core rendezvous to enter the hypervisor shellcode.
8. On success, continue directly to Linux; do not return to GameOS userland.

It followed the original loader's broad timing, but later disassembly showed
that it did not follow the original memory contract or component boundaries.
It is no longer the candidate to test.

## Carrier mapping result

The direct-write carrier preflight was rejected safely before mutation. The
first build expected raw firmware `0x11600000`; the console reported the exact
SDK value `0x11600005`. A refrozen build gated on that exact value then rejected
the candidate mapping before the NOP read or write path. A minimal audited
logging-only delta reported the first leaf as:

```text
PTE entry=0x0400000018acb101
P=1 RW=0 XO=1 NX=0
```

This is a normal execute-only kernel-text mapping. More importantly, it is not
the official/Sonic wake-shellcode location. Public `prepare_resume` maps the
user-backed wake blob into the PID-1 pmap at
`kernel_cave_shellcode=0xffff800000000000`; it does not copy the blob into the
trailing kernel-text padding. Stage 1B already proved data read-through through
that exact PID-1 subtree. The `ktext+0xd2b000` carrier experiment is therefore
retired rather than repaired. All three attempts returned before any write, so
no carrier bytes or page-table entries were changed.

### Earlier pLinux boundary results

A loader-only build read the complete 12,702,720-byte bzImage and
54,367,236-byte initrd, printed the final fetch checkpoint, and exited normally.
The corresponding full pLinux-derived build repeatedly stopped immediately
after printing the initrd-read checkpoint. The same boundary reproduced with:

- a 28,777,476-byte trimmed initrd;
- split and reverse-split source allocations; and
- direct-memory backing after the allocation size was reduced enough to fit.

These results do not show that a coupled payload is too large. The supplied
13.60 ELF is itself coupled and performs more pre-suspend mapping work. They
show that the superseded pLinux-derived full ELF has a layout, state, or latent
memory defect that the loader-only build does not expose.

## Architectural comparison

The upstream source confirms the intended sequence: prepare the resume
shellcode, arm the firmware-specific HV path, request rest, then let the resume
shellcode stage Linux and invoke the all-core VMMCALL rendezvous without a
second userland payload.

An independently supplied ELF reported to support firmware 13.60 provides a
second, binary-level comparison. Its outer ELF is 237,448 bytes with SHA-256
`e51a0298cb2c97b71be0ddad9f070b574c110c899d9fe513562355272fc81226`.
The symbols and disassembly show:

- `main` prepares `shellcode_kernel_bin`, selects `hv_defeat_13xx`, requests
  rest, and then waits;
- the embedded 26,896-byte resume shellcode accepts the 13.xx firmware range;
- its boot routine patches the HV entry, installs the identity map and HV
  shellcode, stages `linux_info`, bzImage, and initrd; and
- the same resume entry then calls the all-core rendezvous.

That ELF is not evidence that the 11.60 offsets or transition are correct. It
is evidence that coupling HV defeat and Linux boot within one resume flow is
the established architecture rather than an arbitrary new design. Deeper
reconstruction also established that its root-0 AP payload only modifies the
VMCBs; a separately installed kernel wake shellcode copies `linux_info` to
physical `0x100005000`, copies bzImage to `0x100009000`, places initrd after its
aligned end, installs the HV transition at `0x100003000`, and starts the final
all-core `vmmcall(1)` rendezvous. See
[Sonic 13.60 binary reference](sonic-13.60-reference.md).

## Superseded source state

The superseded local 11.60 branch is based on pLinux5-NG commit
`d5bd6b9f45c465e466e1e97083c9f162b94aad2c`, with a large uncommitted research
diff. It contains parameterized takeover addresses, runtime bypass validation,
the VMMCALL-specific handler path, and the new wake-coupled wrapper.

The candidate builds cleanly. The wrapper is 2,392 bytes, contains one expected
patch marker, has no final ELF relocations, and is byte-identical when extracted
from the final ELF. Its object contains only PC-relative relocations. The exact
11.60 `HV_MP_STARTUP_CALL` wrapper ABI was also confirmed from the kernel-text
dump: startup ID arrives in `RDI`, payload VA in `RSI`, and payload CR3 in
`RDX`; the wrapper maps them to `EDX`, `RCX`, and `RBX`, sets `EAX=0xF`, issues
`VMMCALL`, and returns with a balanced frame.

The first independent audit found two pre-hardware blockers: seven required
wake parameters were left zero and a handler-byte table was not truly

selection with compact arrival slots and an atomic single-boot election. See
[the candidate audit](11.60-candidate-audit.md).

A second adversarial audit rebuilt the then-current source and verified all five
targeted corrections: the complete wake parameter block, original-startup
ordering and ABI, wrapper position independence, compact arrival slots and
atomic boot election, and the cave/blob bounds. It found no surviving blocker
or new regression within that narrow static scope. Its qualified-GO disposition
is withdrawn after the later hardware failures and Sonic-first architecture
review.
